# Seed data

| File | What it does |
| --- | --- |
| `seed.sql` | Demo restaurant **Spice Route Kitchen**, 10 tables with random public codes, 6 categories, 28 dishes (some with active offers, some sold out), 4 quiz categories with 40 questions, 3 leaderboard prizes, default settings, and 12 historical orders so the reports are not empty. |

Run it after the migrations:

```bash
# Supabase CLI
supabase db reset          # migrations + seed into the local stack
# or paste supabase/seed/seed.sql into the SQL editor of a hosted project
# or, for a plain Postgres / PGlite
psql "$DATABASE_URL" -f supabase/seed/seed.sql
```

The seed is idempotent-ish: it deletes and re-inserts the `spice-route` restaurant (cascading to
its tables, menu, quiz and orders), so it is safe to run again on a demo project.

## Staff accounts are not in the SQL

Passwords must be hashed by the auth provider, so the three demo logins are created separately:

```bash
npm run seed:staff          # admin@ / waiter@ / kitchen@ spiceroute.test, password Demo@1234
```

…or, when using the embedded local database, press **Seed staff logins** on `/setup` after the dev
server starts (the running process owns the in-memory database).

## Table codes

`table_code` values are 24-character random strings generated by the seed (and by
`POST /api/admin/table` / regenerate). They are printed on the QR PDF — never the table number.
